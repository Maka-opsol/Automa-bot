# Patch-validation CI: scope and limitations

This review-branch workflow runs on `pull_request` (not `pull_request_target`), checks tracked JavaScript syntax with the runner's Node, then runs mocked, standard-library-only regression tests. The checkout action is pinned to a full commit SHA and does not persist its read-only token in Git configuration. No npm install, production job, environment, bot credentials, secrets, artifacts, live browser, database or service is used by this workflow. The hosted runner image and preinstalled Node version are not pinned; the workflow requires Node 20 or newer. It does not provision or use a lockfile.

**A green check is deliberately narrow.** It does not typecheck TypeScript, build the bot, validate a staged patch against its actual code, test integrations, run the existing full test suite, prove patch safety, or guarantee that no malicious code executes. PR test code is untrusted and executes on a hosted runner with network access. A PR that changes the workflow or its tests can weaken them: require trusted review of workflow/test changes, use suitable branch protections or organization-controlled required workflows, and never pass secrets or privileged credentials to untrusted PR code. There is no PR or protection created by this branch. Direct writes to main, including dashboard writes, bypass PR checks unless separately prevented.

`test-validation-suite.js` previously treated an unsafe sandbox result object as passing (`result !== false`), and running it as a CLI only loaded exports. It also claimed to validate staged code after `chdir`, although relative imports and injected dependencies still resolve to the already-loaded source. This branch fails closed whenever that function is given a staged path, so normal self-heal promotions relying on that validation will be blocked if this change is merged until real isolated staged-code validation is implemented. This does not fix every promotion path: `self-heal.ts` still falls back to a truthy value if the validator is unavailable and has explicit skip modes. Address those independently before treating this as a promotion security boundary.

The `npm run validate` command may still fail to load runtime dependencies under plain Node because source dependencies are TypeScript and no loader is configured there; failure is not a successful validation. Existing broad dependency versions, missing lockfile and placeholder `lint` are baseline limitations, not fixed by this workflow. No live deployment or production validation was performed.
