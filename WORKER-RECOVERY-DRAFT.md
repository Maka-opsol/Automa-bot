# DRAFT: bounded worker entry-navigation recovery

**Review only. Do not merge or deploy without independent review and a safe, non-academic integration test.** This branch is based on main commit `3c345ef26791749d51da0ac8a4efc6dec15ca37e` and changes only the parallel worker's app-entry navigation.

The dashboard showed a worker's app-root `page.goto` timing out after 60 seconds, with zero completed modules. If that goto receives a 2xx main-frame response for the configured entry URL but times out before DOMContentLoaded, this candidate waits once, up to 15 seconds, on the existing document. It resumes the existing login check only if the browser stays on the entry origin and path. Other errors, missing or unsuccessful response, redirects, and another timeout retain the original failure path. No reload, new navigation, authentication bypass or changed question handling is added.

This is a candidate fix for one narrowly observed timeout path, not proof that the current stall is cured. The logs do not show whether a qualifying response occurred or DOMContentLoaded arrived late. The existing parallel login check can incorrectly report success without verifying authentication; this branch does not fix that separate defect. Flutter timeout, persistence and `pdfjsLib` errors remain unresolved. The PDF diagnostics branch is separate and diagnostic rather than a verified PDF fix. The existing outer worker loop still retries after its normal delay; this change adds no recovery loop.

Offline checks: `node --test test-worker-navigation-recovery.test.cjs`; synthetic page and response mocks only, no network, credentials, academic interactions or submissions. The tests include success, late readiness, timeouts, non-timeout errors, off-origin redirects, missing/error/non-main-frame responses, concurrent workers and extracted coordinator-method integration. Full TypeScript build, real Playwright/browser behavior, the actual deployed revision, live authentication and real recovery are not verified.
