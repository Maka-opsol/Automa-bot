# Browser proxy configuration

Browser traffic is direct unless an operator explicitly configures a proxy. Set `BROWSER_PROXY_URL` in the service's secret environment (not in a committed file), for example `http://HOST:PORT` or `http://USER:PASSWORD@HOST:PORT`. Percent-encode special characters in username/password. IPv6 hosts need brackets. HTTP, HTTPS, SOCKS4 and SOCKS5 URLs are accepted; Playwright Chromium does **not** support authenticated SOCKS, so it is rejected before launch. An HTTP proxy can see HTTP traffic and destination hosts, and a TLS-intercepting proxy can see more: use only a trusted provider and comply with the platform's rules. Do not use this feature to circumvent access controls or rate limits.

**GitHub Actions:** The `mathu-bot-loop.yml` workflow does not map an individual `BROWSER_PROXY_URL` repository secret into the bot's environment. Add a line such as `BROWSER_PROXY_URL=http://USER:PASSWORD@HOST:PORT` to the existing multiline GitHub Actions secret `BOT_ENV_FILE` (using real private values, never committing them). The workflow writes it to `.env` and `scripts/run-bot.sh` loads it with Node 22 `--env-file`; do not print the file or its values. An already-set process environment variable takes precedence over `.env`. A standalone `BROWSER_PROXY_URL` secret will have no effect unless separately mapped in the workflow; this change deliberately leaves the workflow unchanged. Validate in the target deployment before relying on it.

The legacy `PROXY_URLS` environment variable is supported if `BROWSER_PROXY_URL` is absent. Only its first comma-separated entry is used; there is no automatic rotation or direct fallback. Unset both to disable browser proxying. `HTTP_PROXY`, `HTTPS_PROXY`, and `NO_PROXY` are not browser-proxy settings; they may be used independently by other libraries. No proxy URL is written to the application config snapshot or intended to appear in browser launch/worker logs. Proxy credentials are still present in process memory and the environment, and access to both must be restricted. Avoid Playwright debug logs, packet captures and third-party diagnostics that may expose secrets.

The browser manager, updater, selector tester, each parallel context, self-heal investigation browser and Phoenix recovery contexts use the same configuration, with proxy credentials passed separately to Playwright. A malformed URL, authenticated SOCKS, or a runtime policy that disables proxies fails closed. A dead proxy or failed authentication should cause navigation to fail; retries do not deliberately switch to direct access. Existing sessions need a browser restart to apply changed configuration. The `render-free-plan.ts` entrypoint unconditionally disables proxies at startup, including if run outside Render; configuring a browser proxy there causes a safe failure rather than overriding that policy. The current Actions workflow sets three workers, so `run-bot.sh` normally selects `parallel-entry.ts` when that file exists. Other entrypoints and runtime policies must be checked independently. This change disables the prior automatic ProxyScrape discovery/activation instead of sending traffic or authentication to untrusted public proxies. It does not provide IP-rotation or bypass platform restrictions.

Limitations: browser proxy configuration does not cover Node API requests, external providers, or a service mesh. Direct access by those components is outside this feature. Browser DNS, UDP, WebRTC, extensions, loopback behavior, non-Chromium engines, HTTPS-proxy TLS, SOCKS routing and remote deployment have not been comprehensively tested; this is not a network-level leak-proof isolation boundary. Enforce network egress policy externally if strict isolation is required. Pre-existing `ignoreHTTPSErrors: true` is used for the main browser context (`utils-user-agent.ts`), Phoenix tier 2/3 (`browser-phoenix.ts`), and the isolated self-heal investigation (`self-heal.ts`); it disables TLS certificate validation for those contexts, allowing interception by an untrusted intermediary. This patch does not change that behavior and does not provide end-to-end transport protection. Review and remediate certificate validation separately before relying on HTTPS security. HTTP proxy connections can expose proxy credentials on the network; use a trusted encrypted transport where supported and validate the deployment. Protect credentials and validate your provider using a controlled test endpoint before operational use.

Run the local tests with `npx vitest run test-browser-proxy.test.ts` and a Chromium executable at `/usr/bin/chromium`, or set `TEST_CHROMIUM_PATH`. Tests use an ephemeral loopback target and authenticated test proxy; they do not contact MathU or an external proxy.

Clean-room safety: failed tests are ambiguous (including proxy, network, browser and child-process failures), so automatic cache/session purge is disabled for every failed clean-room test; investigate failures manually. This intentionally trades automatic state recovery for avoiding destructive purges.
